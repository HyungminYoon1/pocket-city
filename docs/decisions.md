# 결정 기록

## D01 — 독립 정적 사이트

- 맥락: 네 프로젝트를 별도 GitHub Pages 저장소로 공개 요청.
- 대안: 하나의 사이트 / 별도 서버 기반 사이트 / 독립 정적 사이트.
- 결정: 독립 저장소, 브라우저 JS, 외부 런타임 의존성 없음, dist만 배포.
- 이유: 기존 Pages 운영 방식 유지, 개인정보·운영비 최소화.
- 영향: package.json, dist/, workflow, architecture.md.
- 후속 검토: 공개 배포의 실제 브라우저 검증.

## D02 — 내 기기 기록과 전체 랭킹 구분

- 맥락: 사용자 랭킹 서버는 구축 의견 요청이며 신규 DB는 꼭 필요할 경우에만 허용.
- 대안: 즉시 DB 생성 / 가짜 랭킹 / 기기 내 기록과 서버 제안 분리.
- 결정: 현재 게임·학습 기록만 브라우저에 저장, 기록 삭제 제공. 외부 전송·계정·전역 랭킹 없음. 서버 제안은 구현 상태와 분리.
- 이유: Neon은 DB이며 공개 점수 제출을 검증할 API가 별도로 필요. 비용·보존·위변조 검증을 먼저 정해야 함.
- 영향: core.js, app.js, README.md.
- 후속 검토: 서버 권위 재현/런 티켓/속도 제한과 무료 한도 확정 후 연결.

## D03 — 재현 가능한 도전 코드

- 맥락: 반복 플레이는 무작위, 친구와 같은 문제·판 비교는 동일 조건 필요.
- 대안: Math.random만 사용 / 모든 판 고정 / seed 기반 생성.
- 결정: 새 판은 crypto 기반 seed; 같은 버전·설정·seed면 같은 초기 조건. 입력은 길이·문자 제한. 게임별 규칙 검증과 생성 시험.
- 영향: model, core, app, tests.
- 후속 검토: 클라이언트 점수는 전체 랭킹 증거로 신뢰하지 않음.

## D04 — 규칙과 작업 화면

- 맥락: 시각적인 소개보다 실제 학습·플레이 완주가 중심인 서비스 요청.
- 대안: 공통 카드형 소개 사이트 / 프로젝트별 직접 조작 화면.
- 결정: 20턴 동안 건설 또는 휴식을 선택하고 모든 행동을 순수 모델로 재생합니다. 저장된 스냅샷을 신뢰하기보다 행동을 다시 적용해 이어합니다. 예산이 부족해도 판을 끝낼 수 있게 휴식을 제공하고 완료 판은 최근 10개만 보관합니다.
- 이유: 학습과 플레이 결과를 재현하고 확인할 수 있게 함.
- 영향: dist/src/, dist/index.html, dist/styles.css, test/, README.md.
- 후속 검토: 공개 URL에서 조작과 작은 화면 검증. 기록 보존 범위 변경은 별도 결정 기록 필요.

## D05 — 점수 확장에서 기반시설과 위기 계획으로 (2026-10-09)

- 맥락: 기존 도로는 점수 보너스뿐이고 상점은 정전·단절에도 수입을 냈습니다. 목표 미달도 실패로 판정하지 않아 건물을 늘리는 행동이 전략을 대신했습니다. 이번 자동 구현 세션의 범위는 로컬 구현과 검증입니다.
- 대안: 건물 비용만 인상 / 무작위 재난 추가 / 연결·서비스·수입을 결합하고 예고된 시나리오 도입.
- 결정: 중앙 도로 연결을 순수 BFS로 계산합니다. 연결 발전소만 전력을 공급하고, 도로·주민·전력이 있는 상점만 수입을 냅니다. 공원과 가동 진료소의 생활 서비스, 발전소 인접 오염, 도로 용량·혼잡, 유지비·주민 신뢰를 매 턴 함께 정산합니다. 20턴 상한을 유지하면서 신뢰 0 조기 실패와 최종 목표 전체 달성 승리를 도입합니다.
- 이유: 배치·순서·토지 확보가 서로 다른 결과를 만들도록 합니다. 미지급 유지비는 예산을 음수로 만들지 않고 신뢰를 차감합니다. 4턴 부담 유예, 6턴까지 서비스·환경 부담 유예로 기반시설 건설 시간을 제공합니다. 도로는 항상 제공하고 다른 모든 카드가 3턴 안에 나오며 다음 3턴을 공개하여 운보다 계획의 영향을 높입니다. 중앙 확장 통로는 물 배치에서 보호합니다.
- 결정: 세 임무의 인구·서비스·환경·예산·신뢰 기준을 점진적으로 높입니다. 8·14턴 점검 보상/감점은 복구 가능한 수준으로 제공하며 11턴 지원 종료·폭염·통근 수요를 첫 화면부터 공개합니다. 가동 여부는 현재 도로망과 전력 총량으로 계산하는 유한 추상 모델이며 실제 도시 전력망·의학 모델을 주장하지 않습니다.
- 영향 파일: dist/src/model.js, dist/src/app.js, dist/index.html, dist/styles.css, test/model.test.js, tools/balance.mjs, README.md.
- 후속 검토: 메인 담당자의 브라우저·모바일·키보드 QA와 사람 플레이 난이도 평가. `lesson` 세 임무의 승리 재생은 검증했으나 모든 코드의 해법을 증명하지 않습니다. 제한 탐색이 해법을 찾지 못하는 것은 불가능성의 증거가 아닙니다. 초기 저예산·토지 실수 후 복구 감각은 사람 플레이로 재검토합니다.

## D06 — 규칙 버전과 저장 호환성 (2026-10-09)

- 맥락: v1 행동은 같은 코드라도 v2에서 다른 지형·카드·정산을 만듭니다. 구형 저장을 자동 재생하면 사용자가 만들지 않은 도시와 결과를 표시하게 됩니다.
- 대안: 예전 행동을 새 규칙으로 강제 변환 / 저장 전체 삭제 / 완료 기록 보존과 진행 재생의 버전 검사.
- 결정: 기존 기기 저장 키를 유지하고 v2 진행에 버전·임무·코드·행동만 저장합니다. 완료 기록은 버전·임무·성공 여부·코드·점수·완료 시각을 저장합니다. v1 완료 기록은 따로 표기하고 시간순으로 표시합니다. 버전이 다른 진행은 안내 후 이어하지 않습니다. 기록 삭제를 유지하고 최대 완료 10개 + 진행 1개를 유지합니다. 단계 성공 표시는 최근 완료 기록에서 계산하며 별도 영구 업적·사용자 식별자를 추가하지 않습니다.
- 이유: 규칙 재현성과 기존 완료 기록을 보존하면서 추가 보존 범위·서버·외부 연결을 만들지 않습니다. 세 임무를 모두 즉시 선택 가능하게 하여 저장 불가 환경에서도 진행을 막지 않습니다.
- 영향 파일: dist/src/model.js, dist/src/app.js, dist/index.html, README.md, test/model.test.js.
- 후속 검토: 브라우저에서 실제 v1/v2 저장, 차단된 localStorage, 새 판 확인 취소, 진행 재로딩·삭제를 메인 담당자가 확인해야 합니다. 개인정보·정적 호스팅·CSP 경계와 순수 모델/UI 분리는 유지합니다. 커밋·푸시·배포·DB 생성은 이번 범위 밖입니다.

## D07 — 포커스 미리보기와 완료 버튼 대비 (2026-10-09 QA 후속)

- 맥락: 메인 브라우저 QA에서 칸의 키보드 포커스는 남아 있는데 스크롤 관련 pointerleave가 정산 미리보기를 기본 설명으로 지웠습니다. 완료 패널에서는 기본 버튼의 `color: inherit`가 흰 패널 글자색을 상속하여 흰 버튼에 흰 글자를 표시했습니다.
- 대안: leave/blur 조건만 각각 추가 / 마지막 칸 인덱스를 저장 / 현재 DOM의 포커스·호버 대상을 매번 조회. 버튼은 전역 색 변경 / 완료 패널에만 명시적 대비 지정.
- 결정: 현재 판 안의 활성화된 포커스 칸을 우선하고, 없으면 현재 호버 칸, 둘 다 없으면 기본 설명을 표시합니다. enter/focus/leave/blur와 렌더 완료가 같은 갱신 함수를 사용합니다. 교체된 칸의 지연 이벤트도 현재 판만 조회합니다. `#endgame button`에 기본·hover·focus-visible 글자/배경색과 포커스 외곽선을 명시합니다.
- 이유: 포인터와 키보드 이벤트 순서에 관계없이 현재 조작 대상을 설명하고, 저장한 이전 DOM/인덱스에서 생기는 오래된 미리보기를 피합니다. 버튼 대비 변경 범위를 완료 패널로 제한합니다. 게임 규칙·점수·저장 형식은 변경하지 않습니다.
- 영향 파일: dist/src/app.js, dist/styles.css, test/ui.test.js, docs/verification.md.
- 후속 검토: 실제 스크롤·혼합 입력·버튼 hover/focus 렌더링은 메인 담당자가 수정 후 브라우저에서 재확인합니다. Node DOM 대역의 실제 앱 콜백 회귀 시험과 CSS 대비 계산은 브라우저·이미지 QA의 대체 증거가 아닙니다.
